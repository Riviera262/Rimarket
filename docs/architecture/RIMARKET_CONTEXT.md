## Catalog

Catalog currently contains:

Product
└── ProductVariant
└── VariantImage

Category is a separate hierarchy inside Catalog.

New Catalog entity IDs (Category, Product, ProductVariant and VariantImage) are UUIDv7,
generated by Hibernate. Legacy IDs remain valid and unchanged. UUIDv7 has the same
canonical string length as UUIDv4. Identity's IDs and random token/slug/SKU generation
are outside this Catalog change.

### Category

Rules:

- maximum depth = 3
- no circular hierarchy
- sibling names are unique
- level-1/root categories cannot contain Products directly
- categories with children cannot be deleted
- categories referenced by Products cannot be deleted

Category uses row-level optimistic locking to prevent concurrent admin updates
from silently overwriting one another. Structural write transactions also use
SERIALIZABLE to protect hierarchy decisions spanning multiple rows; conflicts
require reloading data and retrying the whole request. Database unique and
foreign-key constraints remain the final integrity boundary. Concurrent database
integration checks remain pending; see CATALOG_V1_REVIEW.md.

### Product

Product is the Aggregate Root.

Product owns ProductVariants.

Product lifecycle:

inactive/draft
→ add the first active Variant
→ automatically activate Product

Product requires at least one active Variant before activation.

Slug is generated automatically and remains stable after rename.

Products may be assigned only to level-2 or level-3 Categories. Product creation,
Product category changes, and Category moves use the same SERIALIZABLE protocol so a
concurrent Product assignment cannot race a Category move to level 1.

Product carries the optimistic-lock version for the whole aggregate.
Commands that only mutate a ProductVariant force-increment the Product version,
so concurrent variant commands cannot bypass aggregate-level invariants.

### ProductVariant

Variant represents the sellable SKU.

Fields include:

- sku
- name
- price
- sortOrder
- active
- images

SKU is immutable.

Price currently represents VND using BigDecimal / NUMERIC(19,0).

Variants are displayed by sortOrder. New Variants are appended to the end of
their Product; explicit reordering accepts the complete ordered list of Variant IDs.

Product creation, Variant creation, and image upload are separate application
operations. A Product may remain an inactive draft without Variants, and a
Variant may exist before any image is uploaded.

### VariantImage

A Variant owns a list of VariantImages.

VariantImage contains:

- id
- variant_id
- publicId
- url
- sortOrder
- createdAt

Images are ordered using sortOrder. The first image is the cover; there is no separate primary flag.

Image mutation operations include:

- add
- add multiple images in request order
- replace the stored file while preserving image identity and display state
- remove
- reorder

POST /api/management/products/{productId}/variants/{variantId}/images accepts a list
of multipart files named `files` and always returns a JSON array, even for one file.
There is no separate /batch route. Upload validates every file before external I/O,
uploads sequentially, and attaches all image metadata in one Catalog DB transaction.
Known uploads are deleted as compensation if the batch cannot be attached.
Limits are 5 MiB/file, 45 MiB/request and eight images total per Variant.

Catalog's `catalog.outbox_events` schema and historical data are preserved for future
integrations. As of 2026-10-18 the VariantCreated writer example is removed: Inventory
initialization is synchronous, with no Catalog event/publisher/consumer in that path.
See CATALOG_OUTBOX.md.

## Current Development State

Catalog core is close to V1 completion.

Catalog services, controllers and unit tests have been reconciled with the current
first-image-as-cover model. See CATALOG_V1_REVIEW.md for transaction boundaries,
manual SQL rollout, verification evidence and remaining integration checks.

Inventory now has an initial management flow: create a zero-stock item from a Catalog
Variant via the public CatalogVariantLookup contract, read items/history, receive
stock and adjust physical stock with an audit reason. InventoryItem owns quantity
invariants and uses @Version. Commands persist an immutable movement and an Inventory
stock-change outbox event in the same transaction. Actor identity comes from the
authenticated principal; operationId supports safe retries after a committed command.

The only POST /products/{productId}/variants application workflow creates a variant and
Inventory item with optional initial receipt in one transaction through public module
command APIs. The Catalog-only creation handler and /with-stock alias are removed;
Inventory has no HTTP item-creation endpoint. See VARIANT_STOCK_WORKFLOW.md. Event integration,
image snapshots, per-order reservations and outbox publishers remain future work.
As of 2026-10-19, creation also claims (actor_id, operationId) in an application-owned
table and stores the original response in the same transaction. Replays do not create
another variant/item; changed payload with the same key conflicts. Product enforces
unique trimmed, case-sensitive variant names, backed by UNIQUE(product_id, name).
Both additions require the manual migration documented in VARIANT_STOCK_WORKFLOW.md.
See INVENTORY_SCHEMA.md for API examples, transaction guarantees and manual DB rollout.
